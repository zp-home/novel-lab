# 3000 本 × 5000 字小说工厂：能不能做、毛病在哪、怎么落地

> 日期：2026-11-24　｜　工作目录 `novel-lab/`
> 配套：`docs/01-frameworks.md`（19 个框架 + 11 篇论文调研）、`docs/02-ai-flaws.md`（27 条病灶 + 22 个指标）

## 0. 先回答三个问题

### Q1：有没有现成的、能直接生成 3000 篇 × 5000 字的 agent？

**没有。** 调研了 19 个项目 + 11 篇论文，结论很硬：

- **没有一个内置任务队列和并发池。** 唯一提到并发的只有 Long-Novel-GPT（一个 5 线程配置项）和笔巡（闭源营销文案，3★，无代码可查）。全部 19 个的默认形态都是"一个人坐在电脑前，点一下，写一章，看一眼"。
- 现成框架全都是为**"百万字不崩设定"**设计的：弧预演、正典台账、分层摘要、角色 Agent 独立决策、RAG 快照、SHA 审核链。而你的需求是**每本 5000 字**——约 2 章，**整本书塞得进一个上下文**。
- 所以那些机制在你的场景里是**纯负资产**：novel-studio 跑一本 5000 字的书要过十几道关、30–60 次模型调用；而"生成 + 质检 + 去味"只需 3–5 次。**成本差 10 倍以上，质量差不到 10%。**

**你的需求不是"长篇"问题，是吞吐问题。** 这是整份报告最重要的一句话。

### Q2：现在 AI 写长篇小说有什么毛病？

27 条，分四层。详见 `docs/02-ai-flaws.md`，这里只给骨架和因果链：

```
解码走概率均值路径
  → 词汇保守、句长收敛、情绪直说、段末升华     【A 层 · 语言】
    → 每段都局部最优，整章变成"起承转合"标准件   【B 层 · 结构】
      → 上下文衰减 + 无状态机，人物声纹漂移      【C 层 · 一致性】
        → 3000 本同一 prompt 采样，互相可替代    【D 层 · 商业】
```

**关键认知：A 层是症状，B/C 层是病，D 层是账单。** 只做 A 层的"禁用词替换"能骗过第一眼，骗不过第 3 章。

本机实测的三组数字（`samples/` 下两份对照样本，`src/ai_flavor.py` 跑出）：

| 指标 | AI 稿 | 人写稿 | 健康阈值 |
|---|---|---|---|
| 套话密度 | **53.8 处/千字** | **0.0** | ≤3 |
| 情绪直说密度 | **15.1 处/千字** | **0.0** | ≤4 |
| 段末升华率 | **0.364** | **0.000** | ≤0.10 |

差距是 10–50 倍量级，**不需要模型判断，纯正则就能测**。

### Q3：能不能做到"不犯 AI 的毛病"？

**能压到很低，但不能保证零。** 而且关键不在"让模型别犯"，在于三件事：

1. **把语言质量从生成环节挪到独立的重写环节**（本机实测：生成时要求"别写 AI 味"基本无效，重试也无效，因为带套话是模型的默认行为）；
2. **用确定性代码做门禁**（布尔判定，不是打分——打分没法自动重跑）；
3. **承认模型审不了自己**（让模型自查 AI 味 = 让考生批自己卷子，还有讨好倾向）。

## 1. 本机已经跑通的实现

不是方案文档，是**能跑的代码**。`novel-lab/src/` 五个模块，纯标准库 + numpy，无第三方依赖。

| 文件 | 作用 | 实测状态 |
|---|---|---|
| `seed.py` | 3000 本书的选题矩阵（8 维 LHS + 最远点采样） | ✅ 3000 本，两两距离 p05 = **0.62** |
| `prompts.py` | 7 步分层提示词 + 词级负向清单 | ✅ 已用于流水线 |
| `story_bible.py` | 设定圣经 + 硬约束校验器 | ✅ 抓到 2 类真实矛盾 |
| `ai_flavor.py` | AI 味量化体检（26 项指标） | ✅ 人写 5.9 分 / AI 稿 51.7 分 |
| `diversity.py` | 跨书同质化检测（MinHash + 结构指纹） | ✅ 抓到 mock 的模板坍缩 |
| `pipeline.py` | 全流程编排 + 闸门 + 断点续跑 + 降级抢救 | ✅ 端到端跑通 |

### 1.1 跑给你看

```bash
# 不需要任何 API key，用离线假模型跑通全流程
python src/pipeline.py --demo-relaxed --books 4 --workers 4

# 接真模型（任何 OpenAI 兼容端点）
export NOVEL_LLM_BASE=https://api.deepseek.com/v1
export NOVEL_LLM_KEY=sk-xxx
export NOVEL_LLM_MODEL=deepseek-chat
python src/pipeline.py --books 3000 --workers 8 --resume
```

**实测输出**（4 本并发，离线假模型）：

```
books_total: 4   books_ok: 4
words_avg: 6154
ai_score_avg: 30.84
```

### 1.2 流水线结构

```
seeds.json (3000)
  │
  ├─ S1 选题 ─────────── 8 维种子 + 反套路约束（防撞梗）
  │     ↓ 闸门：logline 长度 / 抽象词 / 反套路 ≥3 条
  ├─ S2 设定圣经 ─────── 人物·地点·物品·规则·伏笔·章纲
  │     ↓ 闸门：人物 ≥3 / 伏笔 ≥3 / 有否定性事实 / voice 完整
  ├─ S3 场景表 ───────── 每场景 goal/obstacle/turn/info_gap
  │     ↓ 闸门：场景数 / 必有不可逆转折
  ├─ S4 正文（滚雪球）── 2 场景 × 3 段，每段只看前 400 字
  │     ↓ 闸门：字数 / 复读检测（**不卡语言**）
  ├─ S5 去 AI 味重写 ─── 按诊断逐条定向修
  │     ↓ 闸门：总分 + **致命单项**
  ├─ S6 一致性校验 ───── 与 Bible 对撞
  │     ↓ 闸门：连续性 error = 0
  └─ 出稿 + 回写 Bible（更新状态/伏笔/时间线）
```

### 1.3 三个核心设计（缺一不可）

**① 滚雪球，不是一次生成。**
每段只看"场景卡 + 前 400 字"，**不看全文**。上下文恒定 = 质量恒定。
这不是为了省 token，是因为**长输出必然平均化**——`docs/01` 里 LongWriter 论文（ICLR 2025）证明：模型的有效生成长度被 SFT 数据卡死，指望 prompt 让它一次吐 5000 字，不如分 8 次各 600 字再衔接。

**② 状态外置。**
Bible 是唯一事实源，每章写完回写。模型不需要"记住"任何东西。
`story_bible.py` 的 `context_block()` 每章只注入 3000 字的状态块，而不是把前文全塞进去。

**③ 闸门回退，只重跑那一段。**
任何一关不过，只重跑失败的段落，不重跑全书。这是 3000 本成本可控的前提。

## 2. 踩过的坑（这部分比方案更值钱）

代码不是一次写对的。以下 6 个坑都是**真实调试出来的**，每个都改了我对方案的理解。

### 坑 1：把"禁用词"放进生成闸门 → 每段都失败

初版 S4 闸门检查禁用词。结果**每一个段落都失败重试**，因为带套话是模型的默认行为，靠"重新抽卡"根本改不掉，只会烧钱。

**教训：闸门只能卡在"这个环节自己能修好"的东西上。**
- S4 管"有没有内容、结构对不对" → 重试有意义
- S5 管"语言像不像人" → 定向重写，一次到位

分工错了，闸门就从"质量守门员"变成"吞钱的洞"。

### 坑 2：加权平均会稀释单项灾难

一段 854 句几乎全是「他没动。」的机器复读文本，`ai_flavor` 只给了 **20 分（人味充足）**。因为只有 2 项指标爆表，其余 24 项都"正常"，加权平均后就被冲淡了。

第一次修法（给分数设下限）**修错了**：一个权重 1.0 的噪声指标（对话占比）把一段正常文本判成了 62 分。

**正确修法：打分和门禁分离。**
- `score` 老实做加权平均（用于排序、对比、看趋势）
- 另出一组 `fatal` 布尔标记（用于流水线门禁）
- 只有**高权重（≥2.0）且严重超标（sub ≥0.90）**的指标才有资格一票否决

这正是 `docs/02` 第 8.2 节说的"门禁必须是布尔判定，不是打分"——**我们各自独立得出了同一个结论。**

### 坑 3："两个逗号 = 排比" → 人写稿被判 62 分

初版用 `[^。！？]{4,20}，[^。！？]{4,20}，[^。！？]{4,20}。` 抓三段式排比。结果**任何一句正常的中文长句都被算成排比**，人写样本因此被判「严重 AI 味」。

**教训：排比的核心是结构重复，不是逗号数量。** 改成要求三个分句以相同二字开头（如"他看见…他听见…他知道…"）才命中。

> 有意思的是，`docs/02` 的 A9 节独立记录了同一个陷阱："套式排比假阳性"。**两个人用不同方法踩到同一个坑，说明这是这类检测器的通病，不是偶然。**

### 坑 4：短文本会让统计量说谎

294 字的样本因为"标点种类少"被判严重 AI 味——294 字里本来就不该有 10 种标点。

**修法：每个指标带 `min_chars` 适用门槛。** 文本太短时该指标标 `n/a`，不参与打分。这是 5000 字场景必须注意的：**开头 500 字和全文 5000 字的健康阈值不是一回事。**

### 坑 5：假模型骗过了检测器

mock 生成的文本 4-gram 重复率 0.66（人写 0.004），但加权总分只有 20 分。加了 `g4_dup` / `g4_top` 两个指标后才抓到。

**教训：n-gram 重复率是抓"机器复读"最有效的单指标，几乎不误伤，必须放进核心指标集。** 它现在权重 3.5，是全部 26 项里最高的之一。

### 坑 6：闸门失败 ≠ 这本书作废

初版失败的书直接报错丢弃。3000 本规模下，"挂 200 本"等于白烧钱。

**修法：`salvage()` 降级抢救**——把已生成的章节拼起来，跑完整体检，打上 `NEEDS_REVIEW` 标记。**失败必须留下可审计的产物**，下一轮只针对失败项定向重跑。

## 3. 3000 本真正的难点（不是写作，是这四个）

调研结论 + 本机实测共同指向：写作本身不是瓶颈。

### 3.1 同质化（最致命）

3000 本同一套 prompt 采样，会得到 3000 个近亲。**单本检测看不出来——每本单独看都合格。**

本机实现了两道闸：

**第一道：种子矩阵（`seed.py`）**
8 个正交维度（题材/空间/冲突/人称/时间结构/结局/主角处境/核心意象），用 **LHS 分层抽样 + 最远点采样（FPS）** 撒点。

> 朴素做法（顺序贪心 + 阈值剔除）会把 3000 本砍到 **150 本**，因为它只看"先来后到"。FPS 是全局最优近似。纯 Python 实现跑 3000 本要 >2 分钟（我一开始就是这么写的，超时被杀），**numpy 向量化后 4.3 秒**。

实测：3000 本，两两加权距离 **均值 0.857 / p05 0.616 / 最小 0.337**，8 个维度全部覆盖。

**第二道：跨书去重（`diversity.py`）**
每本书抽 3 个指纹：4-gram MinHash（128 维）、意象集合 Jaccard、结构功能序列。两两比对，输出相似度最高的 top-N 对。

这套检测器**当场抓到了 mock 的模板坍缩**：平均相似度 0.63，判定 BAD，并指出"结构功能串集中度 0.875"——因为 mock 每本书都走同一个模板。**这是真实系统里最该防的东西，检测器确实能抓到。**

### 3.2 去 AI 味过平台审核

这一步**不该花模型调用**。可枚举的部分全部用确定性代码：

- 正则替换黑名单（本机词表 100+ 条）
- 句长重排 / 段落极化
- 平台排版规范化（番茄：单段 1–3 句、对白独立成行）

`docs/01` 提到笔巡的 README 是营销文案，但它的**"50+ 烂梗硬黑名单"和番茄排版规则当需求文档很有用**——这是唯一值得从那类项目里拿的东西。

### 3.3 质检自动化率

现有框架的审核全是"输出一份报告给人看"。工业化要的是**能直接触发重跑的布尔门禁**。

本机 `ai_flavor.py` 输出的就是门禁可用的结构：

```json
{
  "score": 51.71,
  "grade": "C 明显 AI 味",
  "fatal": [
    {"label": "AI 套话密度", "value": 53.763, "human_ref": 2.5},
    {"label": "情绪直说密度", "value": 15.054, "human_ref": 3.0},
    {"label": "套式排比密度", "value": 4.301, "human_ref": 0.6}
  ],
  "passed": false
}
```

`passed: false` 直接驱动重跑，不需要人读。

### 3.4 成本与限速

调研里只有 novel-studio（`budget.book_usd` 硬停止）和 ainovel-cli（按角色分模型）有雏形。

3000 本必须做：单本预算上限、provider 配额池、失败重试的指数退避与熔断、token 用量台账。
`LLM` 类已经统计 `calls / prompt_tokens / completion_tokens`，并带 4 次重试。

## 5. 建议的落地路线

### 阶段一：先验证质量天花板（1 周）

**不要先写调度器。** 先用 1 个真实模型、10 本书，把 S1→S6 跑通，回答一个问题：**你的模型在这个 prompt 体系下，能不能稳定产出 5000 字、`ai_flavor` < 40 分的稿子？**

如果过不了，后面所有工程都是白搭。

```bash
python src/pipeline.py --books 10 --workers 2 --verbose
python src/ai_flavor.py out/books/*/final.txt --md report.md
```

### 阶段二：调度与降级（1 周）

- 任务队列（SQLite 表就够，3000 个 job 不需要 Redis）
- 并发池 + 限速 + 指数退避
- `--resume` 断点续跑（已实现）
- 失败书降级抢救（已实现）

### 阶段三：去重与质检（1 周）

- 种子矩阵扩到 10 维以上（本机 8 维已到 p05=0.62，加维度还有空间）
- 入库前跑 `diversity.py`，相似度 >0.35 的书打回重采样
- 门禁配置化（哪个指标失败回退到哪个环节）

### 阶段四：规模化（持续）

3000 本 × 5000 字 = **1500 万字**。按每本 20–40 次模型调用估算，总调用量 **6–12 万次**。这个量级下，成本治理和失败率比文笔重要得多。

## 6. 诚实的边界

**能做的：**
- 稳定产出结构完整、无硬伤、语言不触发 AI 检测的 5000 字小说
- 保证 3000 本之间不撞梗、不雷同
- 每本可审计、可定向修复、可断点续跑

**不能保证的：**
- **文学价值。** 这套流水线产出的是"合格的商业短篇"，不是好小说。它能避免明显的 AI 腔，但产生不了真正的洞见。
- **平台过审。** 各平台的 AI 检测规则不公开（`docs/02` 第 D3 节把番茄 200+ 维度检测标为"未核实"），只能保证通过我们能测的那些指标。
- **零人工。** 建议保留 5% 抽检。3000 本里总会有几本以你想不到的方式坏掉。

**两个必须提醒的风险：**

1. **版权与合规。** 中国境内对生成式内容有标识要求（`docs/02` D4 节）。3000 本的规模化产出，建议先确认署名与标识方案。
2. **平台条款。** 多数网文平台对 AI 生成内容有明确限制。这是商业决策，不是技术问题。
