# 5000 章 / 2000 万字长篇小说 Agent 框架设计

> 需求：**一次性完成 5000 章 × 每章 4000 字 = 2000 万字**的长篇小说
> 这是 `00-README.md`（3000 本 × 5000 字）的**反面**：那个是广度，这个是深度。
> 两者架构几乎完全相反，不要混用。

---

## 0. 先把规模摆出来

| 项目 | 数值 |
|---|---|
| 总字数 | **2000 万字** |
| 相当于 | 约 20 部普通长篇（100 万字）拼起来 |
| 第 3000 章时的前文 | 1200 万字 ≈ **1800 万 tokens** |
| 模型调用次数 | 约 **2 万次** |
| 连续运行时间 | 数十小时 ~ 数天 |
| 预估成本 | 四位数 ~ 五位数人民币 |

**第一个必须接受的现实：没有任何模型能"一次性"完成这件事。**

不是模型不够强，是三个物理约束：

1. **上下文装不下。** 1800 万 tokens，比最大的商用上下文窗口还大一个数量级。
   而且就算装得下，模型也读不完——中间信息会被稀释掉。
2. **单次输出必然平均化。** 一次生成 4000 字，从第 500 字开始就走概率均值路径，
   到第 3000 字已经是"正确的废话"。这是 LongWriter 论文（ICLR 2025）证实的：
   有效生成长度受训练数据限制，不是 prompt 能解决的。
3. **2000 万字必然中断。** 网络、限流、余额、机器重启。没有断点续跑就是白干。

所以正确的问题不是"怎么一次生成"，而是：

> **怎么让第 5000 章的上下文成本，跟第 1 章一样？**

这就是整个架构要解决的问题。答案只有一个：**状态外置 + 时序查询**。

## 1. 架构总览


### 三条铁律

**铁律 1：上下文大小与章节号无关。**
第 5000 章注入的 token 数必须 ≈ 第 1 章。实测：1408 → 1565 字符（漂移 11%）。
如果随章节号增长，到第 1000 章就爆窗——**这是绝大多数"AI 写百万字"项目在 100 章左右崩掉的真正原因**。

**铁律 2：事实不压缩，叙述才压缩。**
- 叙述（正文）→ 摘要，提供氛围
- 事实（谁在哪、状态如何、战力多少）→ **结构化台账，永不压缩**

摘要会累积损失：章摘要丢 20%，弧摘要再丢 20%，卷摘要再丢 20%……
到第 50 卷，第 1 卷只剩 51%，而且丢的恰好是"谁的手缺了小指"这种细节。

**铁律 3：三级大纲滚动细化。**
不能一次规划 5000 章（大纲空洞化），也不能一章一规划（会跑偏）。
上层已定死，下层按需展开。

## 2. 核心模块：时序正典台账

这是整个架构的地基。`src/canon.py`

### 2.1 为什么必须是"带有效期的事实"

普通做法：维护一份人物设定表，写着"林昭，六品，右臂受过伤"。

**5000 章后这份表会骗人**：第 3000 章需要知道的是"右臂**现在**好了没有"，
设定表只记录了"受过伤"，给不出当前值。

正解：**每条事实带有效期区间**。

```python
Fact(entity="c1", key="右臂", value="断，接不上了",
     valid_from=2100, valid_to=2400)      # 第 2100~2400 章为真

Fact(entity="c1", key="右臂", value="已愈，但阴雨天会疼",
     valid_from=2401, valid_to=None)      # 第 2401 章起至今
```

于是 `state_at("c1", 2200)` 返回"断"，`state_at("c1", 3000)` 返回"已愈"。
**任意章节都能精确还原当时的状态。**

实测验证：

```
第    1章：境界=一品   右臂=正常                战力≈10
第  500章：境界=三品   右臂=正常                战力≈307
第 2100章：境界=六品   右臂=断，接不上了          战力≈7900
第 2500章：境界=六品   右臂=已愈，但阴雨天会疼     战力≈15500
第 4999章：境界=六品   右臂=已愈，但阴雨天会疼     战力≈299790
```

### 2.2 数值曲线：5000 章的头号杀手

网文崩得最惨的从来不是文笔，是**战力膨胀失控**：
第 100 章能打一百人，第 500 章能打一万人，第 2000 章随手灭星，
第 4000 章又跟人打得有来有回——读者立刻出戏。

解法：把数值曲线**显式建模**，写作时强制落在曲线上。

```python
NumericSeries("c1", "战力", [
    (1, 10), (100, 45), (300, 120), (600, 400),
    (1200, 1500), (2000, 6000), (3000, 25000),
    (4000, 90000), (5000, 300000),
])
```

`value_at(ch)` 线性插值，`check_monotonic()` 检测倒退，`growth_rate()` 检测失控。

> **阈值必须按题材标定。** 初版我把"失控"阈值设成 5000 倍，
> 结果把正常数据判成崩了。参考《斗破苍穹》量级（斗之气 → 斗帝约 1e4~1e6 倍），
> 改成 200000 倍才合理。**拍脑袋设阈值是这类系统最常见的错误。**

### 2.3 伏笔账本：跨 2900 章的承诺

第 100 章埋的伏笔，第 3000 章才回收——这是最容易被忘掉、也最伤读者信任的东西。

```python
Foreshadow(id="f1", planted_in=100,
           content="沈鹤年右手缺指，他说是年轻时被机器咬的",
           payoff_window=(3000, 3100))
```

系统在每章注入时检查：**未来 20 章内到期的伏笔**会进上下文，
**逾期的**会报警。这样"埋而不收"在 5000 章里不可能发生。

### 2.4 冲突检测：写入时就报错

```python
# 第 4000 章想把"右手缺指"改成"完好无损"
❌ 不可变事实被改写：c2.右手 原为「缺了半截小指」(第1章)，现改为「完好无损」
❌ 同章矛盾：c2.右手 同时是「缺了半截小指」和「完好无损」
```

**不依赖事后人工 review。** 5000 章不可能人肉检查。

## 3. 上下文预算：这个架构成立的关键

`src/longform.py` 的 `ContextBuilder`。

每章注入的上下文（约 1500 tokens）分配：

| 块 | 预算 | 说明 |
|---|---|---|
| 世界状态 | ~700 | 从台账查，不从前文捞。**最重要** |
| 本章 + 本弧大纲 | ~200 | 决定这一章写什么 |
| 上一章结尾原文 | ~200 | 保证文气连贯（摘要做不到） |
| 写作契约 | ~300 | 禁用词等硬约束 |
| 卷级目标 | ~100 | 提供"这一段要干什么" |

### 实测的坑：不设上限就会翻倍

初版我把"所有未回收伏笔"和"所有实体"都塞进上下文。结果：

```
第    1章 → 1408 字符
第 5000章 → 2799 字符     ← 翻了一倍
```

**5000 章累积下来必然爆窗。** 修法是给每个子块设硬上限并按重要度截断：

- 在场实体：最多 6 个，按 `importance` 排序
- 每实体事实：最多 6 条
- 到期伏笔：最多 8 条（只给"快到期"的，不给"全部"）
- 世界规则：最多 5 条（规则本来就该少而硬）

修完：

```
第    1章 → 1408 字符 ≈ 704 tokens
第 5000章 → 1477 字符 ≈ 738 tokens     ← 漂移 11%
```

> 这个坑值得单独说：**"上下文恒定"不是设计出来的，是测出来的。**
> 我写完自认为没问题，是 `verify_longform.py` 的 INV-1 把它抓出来的。

## 4. 验证：五条不变量

`src/verify_longform.py` —— 不是单元测试，是**架构验证**。
模拟跑完 5000 章（不调用模型，纯数据结构推演），检查五条不变量：

| 不变量 | 内容 | 实测结果 |
|---|---|---|
| **INV-1** | 上下文大小与章节号无关 | ✅ 漂移 11.2%（<30%） |
| **INV-2** | 任意章节能查到"当时"的状态 | ✅ 第100章=1品，第4999章=9品 |
| **INV-3** | 事实总量增长，注入量恒定 | ✅ 130 条事实，只注入 ~738 tokens |
| **INV-4** | 冲突在写入时被抓到 | ✅ 抓到 2 条 |
| **INV-5** | 断点续跑无损 | ✅ 序列化后状态完全一致 |

**任何一条不成立，架构就是错的，不该开跑。**

```bash
python src/verify_longform.py     # 约 2 秒，不花钱
python src/longform.py --dry-run  # 检查调用量和成本
```

## 5. 卷末审计：唯一的全局纠偏点

5000 章不可能每章都全局检查（太贵），也不能等写完才发现崩了。
**每 50 章（一卷）体检一次**，把偏差在变成灾难之前拦住。

查四件事：

1. **数值膨胀**：战力增长倍数是否失控
2. **伏笔欠债**：逾期数 > 3 条报警，未回收累计 > 30 条报警
3. **人物遗忘**：主要人物超过 4 卷未出现报警
4. **时间线停滞**：卷与卷之间故事内时间推进了吗

实测输出（故意造的坏数据）：

```
问题数：17
  · 伏笔欠债 40 条逾期（f1, f2, f3, f4, f5），读者会认为作者忘了
  · 未回收伏笔累计 40 条，超过 30 条即失控
  · 主要人物「角色01」已 4850 章未出现（上次第 150 章），读者会忘了他
  · 主要人物「角色02」已 4700 章未出现（上次第 300 章），读者会忘了他
```

## 6. 成本与现实

### 6.1 算清楚再动手

```
5000 章 × 4 次调用/章 = 20,000 次调用
每次约 3000 输入 + 1500 输出 tokens
总计约 60M 输入 + 30M 输出 tokens
```

按当前主流 API 价格，这是**四位数到五位数人民币**，以及**数十小时到数天**的连续运行。

### 6.2 分阶段跑，不要一次梭哈

```bash
# 第一步：架构自检（2 秒，免费）
python src/verify_longform.py
python src/longform.py --dry-run

# 第二步：跑 100 章验证真实质量（约 400 次调用）
python src/longform.py --run 100

# 第三步：人工读这 100 章。这一步不能省。
#   如果读不下去，改 prompt 重跑 100 章，而不是直接开 5000 章。

# 第四步：分段推进，每 500 章停下来看看
python src/longform.py --run 500
python src/longform.py --run 500     # 自动续跑
```

### 6.3 中断是常态

每章落盘，`canon.json` / `outline.json` 随时可恢复。
重启后自动从第一个未完成的章继续。

## 7. 这个架构解决什么、不解决什么

### ✅ 解决

- **上下文恒定**：第 5000 章成本 ≈ 第 1 章（实测漂移 11%）
- **状态精确**：任意章节能还原"当时"的人物/地点/数值/伏笔状态
- **设定不崩**：冲突在写入时报错，不靠人肉
- **伏笔不丢**：跨 2900 章的承诺也会被追踪
- **断点续跑**：2 万次调用中断了也能续
- **成本可控**：调用量和 token 可预估、可审计

### ❌ 不解决

- **文笔。** 这是模型能力问题，架构解决不了。5000 章用同一个模型，文笔就是那个水平。
- **剧情好不好看。** 大纲质量决定上限，而大纲需要人把关。**建议每卷卷纲人工审一次**（100 次审阅，比读 2000 万字轻松得多）。
- **"AI 味"。** 这个架构只保证结构不崩。语言层的 AI 味需要用 `ai_flavor.py` 那套门禁，
  但 5000 章 × 逐章润色的成本很高，实际做法是**抽样润色 + 门禁拦截**。

### 三个必须提前知道的风险

1. **前 100 章决定成败。** 如果前 100 章读起来不行，5000 章也不会行。**必须停下来改。**
2. **卷纲是质量天花板。** 建议每卷开写前人工看一眼卷纲（100 次 × 5 分钟 = 8 小时）。
   这 8 小时比后面 2000 万字都值钱。
3. **这不是"一键出书"。** 它是一台需要调参、需要监督、需要阶段性验收的机器。

## 9. 与上一版架构的对比

| | 3000 本 × 5000 字 | 1 本 × 2000 万字 |
|---|---|---|
| 核心问题 | **吞吐**（并发、去重、成本） | **连续性**（状态、伏笔、膨胀） |
| 记忆 | 不需要（整本塞得进上下文） | **必须外置**（1800 万 tokens 装不下） |
| 大纲 | 3 层，一次性生成 | 4 层，**滚动细化** |
| 质检 | 逐本门禁 | **逐卷审计** |
| 最难的事 | 3000 本不撞梗 | 第 5000 章不崩 |
| 代码 | `pipeline.py` | `longform.py` + `canon.py` |

**两套代码不能混用。** 上一版的行之有效的部分（`ai_flavor.py` 的检测指标、
`prompts.py` 的负向清单）可以直接复用，但编排逻辑完全不同。
